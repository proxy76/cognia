# Task M2-001: Auth domain models and DTOs

**Milestone:** M2 Auth & Profiles
**Dependencies:** M1-001, M1-007

## Goal
Create auth-specific request and response DTOs (RegisterRequest, LoginRequest, AuthResponse, OAuthGoogleRequest, OAuthAppleRequest, RefreshRequest, RefreshResponse) in the shared module with full kotlinx.serialization support.

## Why This Task Exists
The auth flow requires well-typed request and response models shared between client and server. Defining these DTOs in the shared module ensures both sides serialize and deserialize identically, preventing contract drift and enabling compile-time safety across all targets.

## Source Docs
- docs/06-api-contracts.md (Authentication section)
- docs/04-domain-model.md

## Non-Goals
- No API endpoints or route handlers
- No database queries or persistence logic
- No password hashing or token generation
- No validation beyond what serialization enforces

## Acceptance Criteria
- [ ] All DTOs match the JSON shapes defined in docs/06-api-contracts.md (Auth section)
- [ ] All classes annotated with `@Serializable`
- [ ] RegisterRequest contains email, password, displayName fields
- [ ] LoginRequest contains email, password fields
- [ ] AuthResponse contains userId, token, refreshToken fields
- [ ] OAuthGoogleRequest contains idToken field
- [ ] OAuthAppleRequest contains identityToken, authorizationCode fields
- [ ] RefreshRequest contains refreshToken field
- [ ] RefreshResponse contains token, refreshToken fields
- [ ] All classes compile in the shared/commonMain source set
- [ ] No dependencies on server-only or client-only modules

## Tests Required
- Serialization round-trip tests for each DTO: serialize to JSON and deserialize back, assert equality
- Verify JSON field names match the API contract (e.g. camelCase naming)
- Verify optional fields serialize/deserialize correctly when absent
